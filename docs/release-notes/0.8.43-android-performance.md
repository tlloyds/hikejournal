# HikeJournal 0.8.43 Android performance update

## Release scope

Android + API. This release improves Android cold-start and collection loading and reduces work in the mobile API's species and hike-list queries. It does not change API response shapes, ownership rules, database schema, or Android user flows. `VERSION` and the mobile API semantic version remain `0.8.43`; Android `versionName` is `0.8.43` and `versionCode` is `168`.

## Android

- Persistent Species results now render from disk before the API refresh completes. The cache is scoped to the signed-in account. Existing unscoped Species cache files are migrated only within an authenticated session, and are still cleared when Species data changes or the account is removed.
- Cache reads and writes keep the global cache mutex only for disk access. Network requests for different resources can proceed at the same time, while same-resource loads remain serialized to avoid duplicate fetches. Cached JSON parsing runs on a background dispatcher.
- Nearby areas and field quests load only when the user opens Nearby or Quests. Those two requests now run concurrently, with an in-flight guard that keeps overlapping nearby requests from suppressing the discovery load. A direct Nearby entry starts discovery while its area list is still loading.
- Added release-safe `HikeJournalPerf` timings for HTTP status, elapsed time, response character count, API `Server-Timing` and request correlation ID, cache reads, writes and JSON parsing, and cache-lock wait. Logs omit response payloads, authentication data, and resource IDs.

Offline fallback remains in place. A cache hit is shown immediately while the normal server refresh continues in the background.

## API

- `/v1/species` now reads confirmed observations for visible hike IDs plus unlinked observations, then applies the existing owner and photo visibility checks. It no longer scans confirmed observations for every hike before filtering them in the application.
- `/v1/hikes` now limits confirmed observation reads to visible hike IDs and photo IDs from those hikes. This preserves counts for legacy observations whose hike link is carried by the photo while avoiding a global observation scan.
- No schema migration, endpoint contract, response field, or ownership rule changed. Existing server request timing and `Server-Timing` headers remain in use.

## iOS and Web

- No functional changes.
- No iOS or Web artifacts were built or shipped.

## Performance diagnosis and log triage

The Android repository previously held one shared cache mutex across network fetches in its generic loader and hike loader. That could serialize unrelated requests during a slow response. Species disk data was only used after a network failure, so a valid saved collection did not appear while the first refresh was waiting. The hike-list path also loaded confirmed observation rows broadly to calculate visible per-hike species counts.

The user-reported 29-second delay was not reproduced on a physical Android device in this environment, and no production device-log bundle was available. The new Android timing events and existing API route timing can distinguish local cache wait/read/parse time from server response time on the next run. Expected first loads with no saved data still depend on network and server latency.
